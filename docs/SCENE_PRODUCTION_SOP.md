# Lab Quest｜場景製作 SOP（草案 v0.1）

目標：讓一位老師與 AI 團隊能逐步製作 20–30 個場景，而不是每次重新發明規格或一次重建整個遊戲。本文件是工作流程，不表示列出的場景或功能已完成。

## 先分清三種東西

- **場景**：可走動的空間，例如「物理館電學實驗室」。一個場景可以有多個實驗，並非一個實驗就開一張新地圖。
- **探究事件**：學生自願開始的「現象 → 預測 → 操作 → 觀察 → 解釋／應用」。可以自由重試，不靠走進觸發區強制啟動。
- **環境謎題**：要求把實驗發現用在場景中；不能只有選擇題加門鎖，更不能用不正確的物理效果假裝解謎。

## 每個場景的六道關卡

| 關卡 | 產出 | 老師要決定什麼 | 通過標準 |
| --- | --- | --- | --- |
| 1. 場景提案 | 一頁場景卡：情境、自由探索物件、核心疑問、可玩結尾 | 故事與遊玩目標是否吸引學生 | 能用一句話說出「玩家會做什麼」，不是只列知識點 |
| 2. 科學規格 | 每個實驗的來源、狀態、操作、觀察、不變量與反例 | 科學結論及教學順序 | 老師核准；預測、動畫、判定說同一件事 |
| 3. 灰盒試玩 | 低成本場景、走路、碰撞、主動互動與一條完整探究循環 | 動線、節奏、探索感 | 電腦和橫式手機可玩；路過器材不會誤觸任務 |
| 4. 正式製作 | 器材模型、科學狀態機、畫面內提示、存檔與自動測試 | 美術和操作是否符合預期 | 可進、可退、可重試；不破壞既有場景或存檔 |
| 5. 教學驗收 | 老師真機檢查與少量學生試玩紀錄 | 學生是否觀察、推論、願意繼續 | iPhone Safari 實測；至少記下卡點和科學誤解 |
| 6. 發布 | 版本記錄、回復方式、公開連結 | 是否發布 | 老師同意後才推送；保留可回復版本 |

場景可以在關卡 1–2 反覆討論；**沒有科學規格核准，不做會宣稱物理結果的動畫或判定**。純場景灰盒可以先製作。每次只交付一個可玩的縱向切片，再擴大內容。

## 場景卡的固定欄位

使用 templates/SCENE_CARD.md。至少記錄：場景 ID、狀態、來源教材、核心疑問、玩家主動互動方式、自由探索物件、各事件的輸入／可見結果／成功證據、科學不變量、誤解與重試提示、16:9 觸控配置、素材來源、測試和驗收人。沒有資料就寫「待確認」，不要讓 AI 補猜成定案。

狀態只用五種：構想、待科學確認、灰盒、可試玩、已驗收。版本與狀態分開；「可試玩」不等於「已發布」。場景總表在 SCENE_INDEX.md，一列代表一個空間場景，探究事件記在其場景卡中，避免 30 個場景膨脹成上百份彼此衝突的主企劃。

## 可共用與不可共用

可共用：角色移動、鏡頭、碰撞、靠近提示、主動互動、對話容器、實驗畫面容器、輸入映射、存檔版本、素材載入、QA 工具。第二個場景真正需要相同機制時再抽成共用模組；不要為了尚未出現的 30 個場景先重寫現有原型。

不可強迫共用：摩擦、感應、接觸、電路等不同實驗的科學狀態機；各場景的故事節奏；需要專門操作的器材。資料檔可記錄內容與設定，但不能假定一份 JSON 能生成所有科學互動。

## 交付前的最小驗收

1. **科學**：對照科學規格卡，驗證初始、正確、錯誤與重試狀態；只讓自由電子移動，守恆與流向可被測試。
2. **遊戲**：玩家能自由離開、回來、重新操作；不因單純靠近而被迫看對話或進實驗。環境謎題能用觀察證據理解，不只背答案。
3. **畫面**：16:9 橫式遊戲畫面內看得到所有必要提示與按鍵，不要求往頁面下方捲動；角色與器材不互相遮擋操作點。
4. **裝置**：桌面、iPad 橫式、iPhone Safari 橫式均檢查載入、點擊／拖曳、離開返回和畫面尺寸。瀏覽器模擬先擋明顯問題，但真機是發布前最後一關。
5. **維護**：新增或改變的科學狀態有單元測試；場景互動有瀏覽器測試；檢查載入錯誤、壞資產、存檔向前相容與可回復的提交。
